# Meetily 会议智能助手开发手册

本目录记录本工作区版本从本地会议记录工具扩展为实时会议智能助手的设计与实施过程。文档和代码按依赖顺序同步推进；尚未通过验收的能力不会标记为“已完成”。

## 目标能力

- 同时采集麦克风与系统媒体音频，并保留可追溯的音源信息。
- 接入本地与在线流式 ASR，支持断线恢复、本地降级和可修订结果。
- 使用 MOSS-Transcribe-Diarize 等模型做多人转写、说话人分离与会后校正。
- 增量生成带证据引用的实时会议摘要，并允许管理自定义提示词模板。
- 提供双语字幕与文本同声传译，保证原文优先、译文异步补齐。
- 用悬浮窗口展示字幕、议题、决定和待办，不妨碍查看文档、设计稿或技术方案。
- 建立 ASR、说话人、摘要、翻译、延迟、资源和稳定性评测基线。

截至 2026 年 9 月 2 日，Stage 4.4 已能从项目 `portable\` 目录离线加载固定版本的 MOSS 模型。合成语音的真实 JSONL GPU 验证中，语音路径热启动 RTF 为 0.314，进程 RSS 峰值约 1.851 GB，PyTorch CUDA reserved 峰值约 1.992 GB；静音输入会失败关闭且没有生成文本。该结果证明生产链路可运行，不代表真实多人会议的识别准确率。

MOSS 在当前架构中处理完整音频窗口并异步校正文本与说话人。低延迟悬浮字幕继续由流式 ASR 负责；真实会议、噪声、重叠讲话和长时间运行尚未完成基准测试，因此 Stage 04 仍保留“待验收”项。

Stage 9 已把录音开始时生成的 `session_id` 与受限录音目录哈希持久化，并在保存会议的同一事务中绑定 `meeting_id`。实时摘要是否启用、摘要 handle 是否仍有效，都不会影响这条核心恢复关联。完整翻译事件也会先按可信 session 暂存；窗口重载可直接恢复，会议已经绑定但译文尚未提升时，启动和后续翻译入口会按数据库关联幂等补偿。仍在等待供应商响应、尚未形成完整事件的请求不能跨进程恢复。

## 统一完成标准

每个阶段只有同时满足以下条件才会标记为“已完成”：

1. 主路径具备可运行代码，并兼容已有本地数据或给出明确迁移方案。
2. 核心边界有自动化测试或可复现的人工验收步骤。
3. 失败不会破坏录音和已有会议数据，必要时可降级。
4. 文档记录实际采用的方案、实现中遇到的问题、解决办法、验证结果和未解决限制。
5. 便携版运行数据、模型、缓存和日志继续保存在项目的 `portable/` 目录，不额外占用 C 盘。

## 关键工程原则

- 录音是最高优先级：网络、模型、翻译或总结失败都不能让录音停止。
- 事件而非 UI 是事实来源：转写、说话人、翻译和摘要通过带版本的事件关联。
- 实时结果允许修订：partial、final、MOSS 校正不会靠追加重复文本表达。
- 所有 AI 结论可追溯：摘要中的决定、待办和风险必须能定位到原始话语版本。
- 默认低打扰：悬浮窗不抢焦点、不跳动，鼠标穿透和恢复入口始终可控。
